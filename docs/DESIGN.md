# 设计文档：MiniHttpServer

本文档讲清楚这个服务器**为什么这么设计**，以及它能帮你回答的面试题。建议配合代码一起读。

---

## 1. 从一个问题开始：阻塞式服务器为什么不行（C10K）

第 1 周的阻塞式服务器（`--blocking`）的循环是：

```
accept()  ← 没有连接就一直卡在这
  recv()  ← 客户端不发数据就一直卡在这
  send()
```

问题：**一个线程同一时刻只能服务一个连接**。只要有一个慢客户端，后面的所有连接都要排队。这就是经典的 **C10K 问题**（单机同时处理 1 万个连接）。

要同时处理大量连接，有两条路：

1. **一个连接一个线程**（thread-per-connection）：简单，但线程栈（默认 1MB）+ 上下文切换开销巨大，1 万连接 = 1 万线程，不可行。
2. **I/O 多路复用**（本项目的选择）：**一个线程 + 一次系统调用，同时监听成千上万个连接**，哪个连接就绪就处理哪个。

---

## 2. I/O 复用：select / poll / epoll / IOCP

核心思想：把「等待连接就绪」这件事，从「每个连接一个阻塞线程」变成「一个线程统一等待一批连接」。

| | select | poll | epoll（Linux） | IOCP（Windows） |
|---|---|---|---|---|
| 模型 | 就绪通知 | 就绪通知 | 就绪通知 | **完成通知** |
| 内核实现 | 轮询 + 位图 | 轮询 + 链表 | 事件驱动（红黑树+就绪链表） | 完成端口队列 |
| 复杂度 | O(n) | O(n) | O(1)（就绪数） | O(1) |
| fd 上限 | 有限（默认 1024 / Windows 64） | 无 | 无 | 无 |
| 每次调用是否要重传 fd 列表 | 是（拷贝整张位图） | 是 | 否（内核维护） | 否 |

**select 的三个致命缺点**（面试高频）：

1. **fd 数量有限**：`FD_SETSIZE` 限制（Linux 默认 1024，Windows 默认只有 64！）。本项目里我们用 `#define FD_SETSIZE 1024` 在包含 `winsock2.h` 前把它调大——这本身就是个能讲的点。
2. **O(n) 扫描**：每次 `select` 返回后，要遍历整个 fd 集合找出「谁就绪」，连接多了很浪费。
3. **每次调用都要重传 fd 列表**：`fd_set` 会被内核修改，所以每次调用前都要重新构造、拷贝进内核。

**epoll 怎么解决的**：内核维护「就绪链表」，`epoll_wait` 直接返回「哪些 fd 就绪」，是 O(就绪数)；且 `epoll_ctl` 一次性注册后，不用每次重传。加上**边缘触发（ET）**和 `epollone-shot`，能避免重复通知。

**IOCP 的不同**：epoll 是「就绪通知」（告诉你可以读了，你去读），IOCP 是「完成通知」（你把读请求提交给内核，读完了内核通知你结果）——后者叫 **Proactor**，前者叫 **Reactor**。

> 本项目在 Windows 上先用 **select** 实现 Reactor（结构上和 Linux epoll 的 Reactor 一脉相承），Roadmap 里再升级 IOCP。

---

## 3. Reactor 模式

**Reactor（反应堆）**：一个「事件循环」统一监听所有连接的就绪事件（可读 / 可写），事件到来后**分派**给对应的处理器。

```
while (运行中) {
    就绪事件 = 多路复用等待(读集合, 写集合, 超时)
    for (事件 : 就绪事件) {
        if (是监听socket可读)  接受新连接()
        if (是连接可读)        读取并解析请求()
        if (是连接可写)        发送响应()
        if (是定时器到期)      关闭超时连接()
    }
}
```

本项目的 `Server::run()` 就是这个循环（见 `server.cpp`）。

---

## 4. 线程模型：主 Reactor + 工作线程池

**关键设计决策：I/O 与计算分离。**

- **主线程（Reactor）**：只做 socket 的收和发（`recv` / `send` / `select`），**不跑业务逻辑**。
- **工作线程池**：只跑业务（`handler()` 生成响应），**不碰 socket**。

为什么这么分？

1. **避免 fd 被多线程并发访问**：socket 的读写永远只由主线程做，没有数据竞争，不需要给每个连接加锁。
2. **避免一个慢业务拖垮所有连接**：如果业务处理（比如查库、算东西）在主循环里做，一个慢请求就会阻塞整个事件循环。丢给线程池，主循环保持轻快。

数据流：

```
主线程: recv → 解析出完整请求 → 把 (fd, 请求) 投递给线程池 → 标记该连接 Busy
worker: handler(请求) → 生成响应 → 写入响应队列 → 通过「自管道」唤醒主线程
主线程: 被唤醒 → 取出响应 → 把 fd 注册到可写集合 → select 可写时 send
```

**「自管道」（self-pipe）唤醒**：主线程阻塞在 `select` 上，worker 完成后怎么叫醒它？用一个本机 socket 对（`makeSocketPair()`，因为 Windows 没有 `socketpair`），worker 往写端 `send` 1 字节，`select` 监听的读端就变为可读，主线程被唤醒去取响应队列。这是经典的跨线程唤醒机制。

## 5. 非阻塞 I/O 与 TCP 粘包 / 拆包

TCP 是字节流，**没有消息边界**。客户端发一个完整请求，服务端 `recv` 一次可能只收到一半（拆包），也可能一次收到两个请求（粘包）。

所以：**socket 设为非阻塞**，`recv` 循环读，把数据累积到连接自己的读缓冲（`Buffer`）里，直到 `recv` 返回 `WSAEWOULDBLOCK`（本次读完）。然后用**增量解析** `HttpRequest::tryParse` 判断缓冲里是否已有一个完整请求：

- 先找 `\r\n\r\n`（请求头结束标志）；
- 再根据 `Content-Length` 判断 body 是否读齐；
- 齐了才解析，没齐返回 `NeedMore`，继续等下一次可读。

这样无论数据怎么分块到达，都能正确切出一个个完整请求。

## 6. 定时器：最小堆 + 懒删除

keep-alive 连接可能长时间空闲，需要超时回收（比如 60 秒）。

- 每个连接有一个 `deadline`（最后活跃时间 + 空闲超时）。
- 用 **最小堆**（这里用 `std::priority_queue`）按 deadline 排序，堆顶就是最早到期的连接。
- `select` 的**超时参数**设为「距堆顶到期还剩多少毫秒」，这样既能阻塞等事件，又能准时醒来处理到期连接。
- **懒删除（lazy deletion）**：连接的 deadline 更新时，旧条目不清除（堆里删除代价高），而是留着变成「过期条目」；`tick()` 弹出堆顶时，用 `deadlineOf_[fd]` 核对是否还是有效 deadline，不是就跳过。这样删除是 O(1)，摊销 O(log n)。

---

## 7. 内存池：空闲链表

高频的「新建连接 → 分配读缓冲 → 关闭连接 → 释放」会带来大量 malloc/free，产生开销和碎片。

内存池：预先 `malloc` 一大块内存，切成固定大小的 block，用**空闲链表**串起来。`allocate()` 从链表头取一块，`deallocate()` 放回链表头，都是 O(1)，不触发系统调用。

本项目用它做连接的读缓冲（`Buffer`），块大小 64KB = 单个请求上限（超出回 413）。

---

## 8. 编码过程中踩的坑（好素材）

1. **MSVC 读 UTF-8 源码报 C4819**：中文注释是 UTF-8，MSVC 默认按 GBK 读，导致一堆虚假语法错误。解法：加 `/utf-8` 编译开关。
2. **命名空间 `log` 和 C 库 `log()` 撞名**：`<cmath>` 里的 `log` 是求对数函数，不能再用 `log` 做命名空间，改成了 `logging`。
3. **「最让人烦恼的解析」**：`std::istringstream ls(std::string(s));` 会被编译器当成函数声明，要用 `std::istringstream ls{std::string(s)};`。
4. **Windows 的 `FD_SETSIZE` 默认 64**：不改的话 select 最多管 64 个连接。

## 9. 面试高频题 Q&A

**Q：select 和 epoll 的区别？为什么 epoll 更快？**
A：见第 2 节表格。三个点：fd 上限、O(n) vs O(1)、每次重传 vs 内核维护。

**Q：什么是 Reactor？**
A：事件循环 + 分派。一个线程用多路复用监听所有连接，就绪后分派给处理器，见第 3 节。

**Q：你的线程池怎么实现的？**
A：固定 N 个 worker 线程 + 一个任务队列（`std::deque`）+ `mutex` + `condition_variable`。`submit` 加任务并 `notify_one`，worker 在 `wait` 上醒来取任务执行；析构时置 `stop` 并 `notify_all`，join 所有线程。

**Q：为什么主线程只做 I/O？**
A：避免慢业务阻塞事件循环；同时保证 socket 只被一个线程访问，无需加锁，见第 4 节。

**Q：怎么处理粘包 / 拆包？**
A：非阻塞循环读 + 缓冲 + 增量解析（`\r\n\r\n` + `Content-Length`），见第 5 节。

**Q：keep-alive 空闲连接怎么回收？**
A：定时器 + 懒删除，`select` 超时参数驱动，见第 6 节。

**Q：内存池解决了什么？**
A：高频固定大小对象分配的 malloc 开销和碎片，空闲链表 O(1)，见第 7 节。

**Q：压测瓶颈在哪？怎么优化？**
A：本机回环下瓶颈在 CPU/调度；生产环境瓶颈在网络与内核。优化方向：IOCP/epoll 替代 select、减少数据拷贝、更精细的锁粒度、`SO_REUSEPORT`（Linux）多线程监听。
